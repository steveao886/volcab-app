# Volcab v1.1 — 六项功能设计

日期:2026-07-25
状态:已与用户确认
前置:v1.0(Phase 1–4)已上线于 https://steveao886.github.io/volcab-app/,用户正在真机使用

## 1. 背景

v1.0 上线后用户在真机使用中陆续提出六项需求。六者互相独立、各自可单独上线,故合并为一份路线图,分节设计,按 **A → F → D → B → C → E** 顺序实施。

| | 功能 | 触及范围 |
|---|---|---|
| A | 复习流程微调 | 仅复习页 |
| B | 音效 | 新模块 + 设置项 |
| C | 词频评分 | 数据管线 + 词条详情页 |
| D | 学习数据可视化 | 今日页 + 新增 `/stats` 页 |
| E | 生词暂存区 | `volcab-data` 新增文件 + 同步引擎 + `/add` 页 |
| F | 新增测验题型 | 仅 `src/lib/quiz.ts` + 测验页渲染 |

**A、B、D、F 纯前端。C 改写 `words.json`。E 是唯一动数据仓库结构的一项**(新增第三个文件并接入同步),因此实施成本最高,排在最后。

**F 是唯一需要修改既有测试断言的一项**(见 §7.5),其余各项只新增测试。

**C 与 E 应当合并执行一次生成**:E 的补全流程本来就要生成完整词条,若 C 已落地,新词就该在入库时直接带上 `usageScore`,而不是先入库、事后补一轮评分。

## 2. A —— 复习流程微调

### 2.1 进度显示改为剩余张数

**问题**:复习页顶部显示 `16/60`,而用户设置的每日新词数是 50,数字对不上,第一反应是算错了。

**成因**(非缺陷):会话队列的分母 `total` 初始为「到期词 + 新词」,每当一张卡打分后仍处于 `learning` 且当天仍到期,它被插回队尾且 `total` 加一(`src/pages/reviewQueue.ts`)。一个新词走完学习步长通常要看两次以上,所以分母必然大于 `newPerDay`。当初这样设计是为了避免分母钉死时进度条永远走不满。

**改为**:显示 **`还剩 N 张`**(`N = total − seen`)。单调递减至 0,不会与任何设置矛盾;卡片重现只让它下降变慢,而不是让一个数字变大。进度条本身保留,`aria-valuenow` / `aria-valuetext` 相应调整为剩余语义。

### 2.2 复习卡上删除词条

**动机**:复习时遇到不想要的词,当场剔除,而不是记下来事后去词库页找。

**行为**:
- 删除入口**只在翻面后出现**。未看释义时无从判断该不该删;且正面只有词头与发音两个大目标,加一个不可逆按钮误触代价过高。
- 位置在四个打分键**之外**(卡片底部靠边),不与打分区混排。
- 点击后走已有的 `ConfirmDialog`,文案沿用词条详情页那套:说明该词的学习进度会一并清除且无法恢复。
- 确认后调用 `deleteWords([id])`,并对会话队列调用已有的 `dropCurrent()` —— 摘掉队首、不计入 `seen`、`total` 减一。继续下一张,**不结束会话**。
- 队列清空则进入完成页,与正常打完一致。

**复用**:`dropCurrent()` 是 Task 17 为「另一台设备删掉了当前词」这一场景写的,语义完全吻合,无需新增队列逻辑。

### 2.3 验收

- 设置每日新词数为 N,进入复习页,剩余张数随打分单调递减,重现的卡片使其下降变慢而非上升。
- 翻面前无删除入口;翻面后有;点击弹出确认;取消则无事发生。
- 确认删除后:该词从词库消失、其 `progress.words[id]` 被清除、剩余张数减一、界面停在下一张卡。
- 删除最后一张后进入完成页,不报错。

## 3. B —— 音效

### 3.1 方案

**Web Audio API 现场合成**,不引入任何音频文件。理由:无需音频素材授权;不增加 Service Worker 预缓存体积;天然离线可用;音高与时长随时可调。与「墨与纸」这套克制的视觉语言相符 —— 短促的合成音比录制音效更贴。

封装为单一模块 `src/lib/sound.ts`,对外暴露语义化接口(如 `playGrade(grade)` / `playQuizResult(correct)` / `playSessionDone()`),调用方不接触 Web Audio 细节。日后若改为音频文件,只替换该模块。

### 3.2 发声位置

只有三处:

| 事件 | 声音 |
|---|---|
| 四个打分键 | 四个短音,音高按 重来 → 困难 → 良好 → 简单 **上行**,与已有的「热→冷」四色温度带对应 |
| 测验判对 / 判错 | 两个明确区分的短音 |
| 复习会话完成 | 一个稍长的完成音 |

**翻面与底部导航切换不发声** —— 每张卡都要翻,加音会迅速变成噪音。

### 3.3 约束

- **默认开启**。设置页提供开关,存于 `progress.settings`,随进度同步到其他设备。

  > **写这句时它还是假的。** `mergeProgress` 当时的最后一行是 `settings: local.settings` ——
  > 合并一律取本地,于是 `settings` 在两台设备之间**永远无法同步**:A 改了推上去,
  > B 拉下来合并时本地赢,再推回去就把 A 的改动冲掉。用户先在每日新词数上撞到了
  > 这个问题。已改为按 `settings.updatedAt` 判优(与词条进度按 `lastReviewedAt`
  > 判优同一套思路),缺时间戳视为最旧,让「从未改过设置的设备」跟随「改过的设备」。
  > 教训:写「随进度同步」这类断言前应当去核对合并规则,而不是假定 `progress.json`
  > 里的东西就都会同步。
- **iOS 必须在首次用户手势中解锁 `AudioContext`**,否则后续播放静默失败。这是此类功能最常见的失败模式,须在首个用户交互(如登录成功或首次打分)时 `resume()`。
- 不受 `prefers-reduced-motion` 影响 —— 该媒体查询针对动效,声音由独立开关控制。
- 音量适中、时长控制在百毫秒级,避免与系统提示音混淆。

### 3.4 验收

- 开关关闭时完全静默;开启时三处按预期发声。
- iOS Safari 上首次交互后即可发声(此项须真机验证)。
- 离线状态下音效正常(合成不依赖网络)。
- 开关状态在另一台设备登录后一致。

## 4. C —— 词频评分

### 4.1 数据模型

`src/types.ts` 的 `Word` 增加**可选**字段:

```ts
/** 当代遇见概率 1–10:在真实语境里碰到这个词的可能性。缺省表示尚未评分。 */
usageScore?: number
```

**可选而非必填**:用户在 App 内手动添加的词不会有分数,`AddWord` 不应为此增加输入项。详情页在缺省时不渲染该格,而不是显示 0。

**兼容性**:`scripts/validate-words.ts` 与 `src/state/sync.ts` 的 `isWord` 均不检查多余字段,故新旧数据双向兼容 —— 旧版 App 读新数据不崩,新版 App 读旧数据仅不显示分数。

**校验**:`validate-words.ts` 增加一条 —— 若 `usageScore` 存在,必须是 1–10 的整数;不存在则放行。

### 4.2 评分标准

尺度锚定在**「你会在哪里碰到它」**,而非抽象词频数值。

| 分 | 含义 | 示例 |
|---|---|---|
| 9–10 | 职场邮件、新闻标题即会出现,不认识会直接卡住理解 | `status quo`、`due diligence` |
| 7–8 | 主流媒体正文、商业科技报道定期出现,泛读每周可能碰到 | `ad hoc` |
| 5–6 | 正式书面语常见、口语少见;**或**专业领域内高频而领域外罕见 | `concoct`、`nonrepudiation` |
| 3–4 | 严肃长文、文学、法律文本偶尔出现,当代日常几乎不用 | `abrogate` |
| 1–2 | 罕见或古旧,基本只活在词典与备考材料中 | `grandiloquence`、`circumlocution` |

**两条必须写死的规则:**

1. **专业术语统一落在 4–6**,按其在该领域文档中的高频程度评定,而非按通用语料频率。否则信息安全、医学、化学、修辞那批术语会被一律压到 1 分 —— 而它们是词库构建时特意加回来的。仅当该词已溢出到日常语言(如 `algorithm`、`bandwidth`)才可给到 7 以上。
2. **每批评分必须携带同一组锚点词及其给定分数**,强制所有批次使用同一把尺。缺少这一步,十余个批次会各自漂移,7 分与 5 分之间失去可比性。这是 Phase 2 生成词库时未做、事后看应当做的事。

### 4.3 生成管线

- 分批评分,每批约 40 词,可并行派发。
- 每批提示词包含:分档表、两条规则、锚点词及其分数。
- 合并后检查**分布**:若九成词挤在 1–3 档,说明标准未被执行,该批重评而非将就。
- 通过 `npm run validate-words` 后写回 `data/words.json`,再推送至 `volcab-data`。

**覆盖策略**:直接覆盖。已实测本地 `data/words.json` 与 `volcab-data` 中的副本逐字节相同(SHA-256 一致,476 对 476,无增删改),故无需合并逻辑。**若日后用户已在 App 内改动词库,此策略失效,必须改为「以云端为基准逐词补字段」。**

### 4.4 展示

**仅在词条详情页**,在现有学习状态四格(状态 / 到期 / 复习次数 / 失误次数)旁增加一格,复用已提升的 `.stat` 原语。词库列表与复习卡**不显示** —— 列表 476 行密度已高,复习卡应聚焦记忆本身。

### 4.5 验收

- 476 词全部有分,取值均为 1–10 整数,`npm run validate-words` 通过。
- 分布跨越各档,不出现九成集中于某一两档。
- 抽查:`status quo` 一类明显高于 `grandiloquence` 一类;专业术语落在 4–6 且未被压到 1–2。
- 详情页显示该格;手动添加的无分数词条不显示该格且不报错。

## 5. D —— 学习数据可视化

### 5.1 数据边界(关键约束)

设计文档的「非目标」明确不存完整复习日志,`progress.json` 每天仅四个聚合数:`reviewed` / `newLearned` / `correct` / `quizTaken`。**本功能不改变该结构。**

理由不只是遵循原设计:`progress.json` 与 `words.json` 走同一套 GitHub Contents API,同样受 1 MB 读取上限约束。按每日 50 张卡、每条日志约 80 字节估算,一年约 18000 条 ≈ 1.4 MB —— 约 9 个月后新设备将无法登录。完整日志需配套归档或更换存储方案,不在本次范围。

**因此可做**:每日复习量、正确率趋势、连续天数与断签、掌握度随时间增长、词库状态分布、累计量。
**因此不可做**:单词级复习历史、时段效率分析、每卡停留时长、遗忘曲线拟合。

### 5.2 位置

- **今日页下方新增「最近」一块**:近 7 天复习量柱状图 + 正确率,一眼可见近况。
- **新增 `/stats` 页**承载完整统计,入口在今日页的「最近」一块上。
- **不占底部导航第五格** —— 四格(今日/词库/测试/设置)已满,挤入第五格会破坏移动端手感。

### 5.3 指标清单

- 近 30 天每日复习量(柱状)
- 正确率趋势
- 连续天数,以及断签日历(哪天断的)
- 词库掌握分布:未学 / 学习中 / 已掌握
- 累计:总复习次数、已掌握词数
- 平均每日新词消化量

全部由 `dailyStats` 与各词的 `state` 派生,**不引入图表库** —— 以现有设计令牌手写 SVG/CSS,与 `.progress`、`.stat` 等既有原语保持一致。

### 5.4 验收

- 无数据(新用户)时各图表显示合理空状态,不出现 `NaN` 或空白区域。
- 仅有一天数据时不报错。
- 375px 下不横向溢出;深浅色两套均可读。
- 派生数值与 `progress.json` 手工核算一致。

## 6. E —— 生词暂存区(staging)

### 6.1 动机

手机上填完一个合格词条要十个字段,而看到生词的那一刻不记下来就会忘。**捕获与补全必须分离**:设备上只记单词,补全交给会话中的 AI 批量完成。

### 6.2 数据位置

`volcab-data` 新增第三个文件 **`staging.json`**:

```json
{ "version": 1, "items": [ { "headword": "ostensible", "addedAt": "2026-07-25" } ] }
```

**为什么单独一个文件而不是塞进现有两个**:放进 `words.json`,半成品词条会通不过 schema 校验,并且会直接进入复习队列;放进 `progress.json`,它会卷进那套为学习进度设计的按词合并逻辑。单独文件 = 独立的冲突域。

**条目只有两个字段。** 不设备注、不设来源、不做词典预查 —— 用户明确要求「添加时只有单词,其余全部由 AI 产出」。补全时若需要区分义项,由 AI 在生成阶段自行判断,或在会话中回问用户。

### 6.3 捕获入口

复用现有 `/add` 路由,**不新增导航项**:

- 页面**顶部**是快速收词:一个输入框 + 「加入待补全」。这是默认看到的东西。
- 现有的完整表单保留在下方(或折叠),用于「我现在就想完整添加」的场景。
- 页面显示当前待补全数量(「待补全 N 个」),让用户知道攒了多少。
- 去重:大小写与首尾空白归一后,已在 `words.json` 或已在 `staging.json` 中的词直接提示,不重复入列。

### 6.4 同步

`staging.json` 需要接入同步引擎,但规则比 `progress.json` 简单得多:

- **合并 = 按归一化后的 headword 取并集**,同词保留较早的 `addedAt`。追加为主、天然幂等,不需要 `lastReviewedAt` 那套按词比较。
- 沿用 `words.json` 的推送时机(变更即推,不防抖)与冲突重放策略。
- 离线时入列先落本地,联网后合并推送 —— 与现有词库改动同一套待推送队列机制。

### 6.5 补全流程(会话内,非 App 内)

1. 读取 `staging.json`。
2. 分批生成完整词条,复用 Phase 2 的生成提示词,并**同时产出 C 的 `usageScore`**(两件事一次做完,不要让新词缺分数)。
3. 过 `npm run validate-words`。
4. 合并进 `words.json`(按 id upsert),**从 `staging.json` 中移除已提升的条目**(按 headword 精确移除,而非清空整个文件 —— 用户可能在我工作期间又加了新词)。
5. 推送两个文件。

生成的词条**直接进入词库并参与复习**,不设待确认状态。若某条不对,用 A 提供的「复习卡上删除」当场剔除即可。

### 6.6 验收

- 手机上输入一个词 → 加入待补全 → 另一台设备登录后能看到同一条。
- 重复词、已收录词被正确拦下。
- 离线入列,联网后自动同步。
- 补全后 `staging.json` 只移除了被提升的条目,期间新加的词仍在。
- 新收录的词条带 `usageScore`,且能通过 schema 校验。

## 7. F —— 新增测验题型

### 7.1 目标

现有三种题型(看词选义 / 看义选词 / 拼写)只覆盖「中英互认」与「拼写」。新增三种,把记忆从孤立词义扩展到**真实用法、搭配与语义网络**。

### 7.2 数据可行性(实测,非估计)

对 476 词全量统计:

| 候选 | 可出题比例 | 结论 |
|---|---|---|
| 例句挖空 | **100%**(86% 例句含词头原形,14% 仅含变形,0% 无法定位) | 采纳 |
| 搭配填空 | **100%**(全部词条 ≥2 条搭配) | 采纳 |
| 近义/反义提示选词 | 近义 97%(≥3 同义词)、反义 83%(≥1 反义词) | 采纳 |
| 反义词四选一 | **仅 18%**(≥3 反义词) | **否决** |
| 听音选词 | 100% | 本次不做 |

**「反义词四选一」被否决的原因值得记录**:四选一需要 3 个干扰项,而只有 18% 的词条拥有 ≥3 个反义词,出题池会反复抽中同一小批词。**但把出题方向反过来**(给出一个反义词、选目标词,干扰项从其他词头抽取)只需要 1 个反义词,可行率跃升至 83%。同一知识点,出题方向决定可行性。

### 7.3 三种新题型

**例句挖空** —— 取该词的一条例句,把词头替换为 `___`,四个词头选一。
- 14% 的例句中词头以变形出现(`concocted` / `concocting`),需按词干定位并整体替换,不能只做全词匹配。
- 选中的例句在挖空后**不得再包含该词头**(避免同句中出现第二次而泄题)。
- 选项为四个词头**原形**,不还原变形形态 —— 顺带考察「这个词是否适配该语境」。

**搭配填空** —— 取一条搭配(如 `abrogate a treaty`),挖去词头部分 → `___ a treaty`,四个词头选一。

**近义/反义提示选词** —— 提示为一个近义词或反义词(界面须标明是哪一种),四个词头选一。
- **必须排除被多个词条共享的同义词**:实测 1597 个同义词中有 228 个出现在一个以上词条(如 `overbearing`、`decree`、`flexibility`)。用它们作提示会导致「两个选项都对」,用户会判定测验有缺陷。
- 干扰项还须校验:不得包含同样拥有该提示词的其他词条。

### 7.4 题型轮换

保持现有的**确定性轮换**(`types[i % types.length]`),仅扩展题型列表。理由:轮换保证每轮题型分布均衡,避免随机导致「连续三道拼写」这类坏运气。6 种题型、10 题一轮,每种出现 1–2 次 —— 交错练习本身有利于记忆,不视为缺点。

**不做题型选择器**:增加设置项与界面复杂度,而收益是让用户可以回避自己不擅长的题型,与「多方面加深记忆」的初衷相反。

### 7.5 对已有测试的影响(须有意为之)

`src/lib/quiz.test.ts` 现有断言 `expect(new Set(qs.map(q => q.type)).size).toBe(3)` 在题型扩展后**必然失败**。这是本项目第一次需要修改既有测试的断言,须作为一次明确记录的改动,而非实施中顺手改掉。修改后的断言应表达真实意图:**题型在一轮内均衡轮换**,而不是硬编码某个数字。

新题型的生成逻辑全部位于 `src/lib/quiz.ts`(纯函数,已有测试文件),**强制 TDD**。

### 7.6 验收

- 六种题型都能出题,一轮 10 题中分布均衡。
- 例句挖空:挖空处不残留词头,含变形的 14% 词条同样能正确挖空。
- 搭配填空:提示中不含答案词。
- 近义/反义题:提示词标明近义还是反义;不出现两个选项皆正确的情况(针对 228 个共享同义词专门验证)。
- 词库不足 4 词时仍正确降级(现有行为不变)。

## 8. 跨功能约束

- **不引入新的 npm 依赖。** 音效用 Web Audio,图表手写。
- **沿用既有设计系统**:`.stat` / `.empty-state` / `.confirm-dialog` / `SyncStatus` 等已提升的原语;朱砂仅作批注色;发丝描边而非阴影;`--tap: 44px` 最小可点区域。
- **有真实逻辑的部分强制 TDD 并单独成文件**,与 Phase 3 一致(剩余张数计算、统计派生函数等)。UI 本身不写组件测试。
- **实施顺序 A → F → D → B → C → E**,各自独立可上线,互不阻塞。F 紧随 A(同属复习/测验体验,且纯逻辑改动);C 先于 E,使 E 补全的新词一入库即带 `usageScore`。

## 9. 非目标

- 不改 `progress.json` 结构,不存复习日志。
- 不做遗忘曲线、时段分析、单词级历史。
- 不引入图表库或音频素材。
- 不改动 SRS 调度算法本身。
- 不为 `usageScore` 增加手动录入界面。
- 不占用底部导航第五格。
- 暂存区不设「待确认」状态、不在 App 内做词条审核界面。
- 暂存条目不记备注、来源或原句 —— 捕获必须保持一个输入框的成本。

## 10. 已知的遗留风险(非本次范围,但相关)

- `words.json` 已占 GitHub Contents API 1 MB 读取上限的 53%(559,937 字节 / 476 词),约再加 415 词即触顶,届时新设备无法登录。修法是读取时改用 `Accept: application/vnd.github.raw`,上限提至 100 MB,改动集中在 `src/lib/github.ts` 的 `getFile`。C 增加的字段会使该文件小幅变大,应在实施 C 时复测占比。
