# Volcab v1.1 — Six-Feature Design

Date: 2026-07-25
Status: confirmed with user
Prerequisite: v1.0 (Phase 1–4) is live at https://steveao886.github.io/volcab-app/, the user is using it on a real device

## 1. Background

After v1.0 shipped, the user raised six requests over the course of using it on a real device. The six are independent of each other and each can ship on its own, so they're combined into one roadmap here, designed section by section, implemented in the order **A → F → D → B → C → E**.

| | Feature | Surface area |
|---|---|---|
| A | Review-flow tweaks | Review page only |
| B | Sound effects | New module + settings item |
| C | Usage-frequency scoring | Data pipeline + entry detail page |
| D | Learning-data visualization | Today page + new `/stats` page |
| E | Staging area for new words | New file in `volcab-data` + sync engine + `/add` page |
| F | New quiz question types | `src/lib/quiz.ts` only + quiz page rendering |

**A, B, D, F are pure front-end. C rewrites `words.json`. E is the only one that touches the data repo's structure** (adds a third file and wires it into sync), so it has the highest implementation cost and is scheduled last.

**F is the only one that requires modifying an existing test assertion** (see §7.5); everything else only adds new tests.

**C and E should be run as a single generation pass**: E's completion flow already has to generate a full entry, so once C is in place, new words should get `usageScore` at intake time rather than being scored in a separate pass after the fact.

## 2. A — Review-flow tweaks

### 2.1 Progress display switches to "cards remaining"

**Problem**: the top of the review page shows `16/60`, while the user's daily new-word setting is 50 — the numbers don't line up, and the first reaction is that something's miscounted.

**Cause** (not a bug): the session queue's denominator `total` starts as "due words + new words," and every time a card is graded and is still `learning` and still due today, it's reinserted at the end of the queue and `total` gets incremented (`src/pages/reviewQueue.ts`). A new word usually needs to be seen more than twice to get through the learning steps, so the denominator is necessarily larger than `newPerDay`. This was originally designed this way so the progress bar wouldn't stall at a fixed denominator forever short of full.

**Change to**: show **`N left`** (`N = total − seen`). Monotonically decreasing to 0, never conflicting with any setting; a card reappearing only slows the decrease, it doesn't make a number go up. The progress bar itself stays, with `aria-valuenow` / `aria-valuetext` adjusted to match the "remaining" semantics.

### 2.2 Deleting an entry from the review card

**Motivation**: when an unwanted word shows up during review, remove it on the spot instead of noting it down to go find later on the word-list page.

**Behavior**:
- The delete entry point **only appears after flipping the card**. Before seeing the definition there's no way to judge whether the word should be kept; and the front only has two big targets, headword and pronunciation — adding an irreversible button there would make mis-taps too costly.
- Positioned **outside** the four grading buttons (tucked at the edge of the card's bottom), not mixed in with the grading area.
- Tapping it goes through the existing `ConfirmDialog`, with wording matching what's used on the entry detail page: explains that the word's learning progress will be cleared along with it and can't be recovered.
- On confirm, calls `deleteWords([id])`, and calls the existing `dropCurrent()` on the session queue — drops the head of the queue, doesn't count toward `seen`, decrements `total` by one. Continues to the next card, **doesn't end the session**.
- If the queue empties out, it goes to the completion page, same as finishing normally.

**Reuse**: `dropCurrent()` was written in Task 17 for the scenario "another device deleted the current word" — the semantics match exactly, no new queue logic needed.

### 2.3 Acceptance criteria

- Set the daily new-word count to N, enter the review page, cards-remaining decreases monotonically as you grade, and a reappearing card slows the decrease rather than increasing it.
- No delete entry point before flipping; present after flipping; tapping it pops a confirmation; canceling does nothing.
- After confirming a delete: the word disappears from the word list, its `progress.words[id]` is cleared, cards-remaining decreases by one, the UI stays on the next card.
- Deleting the last card goes to the completion page without error.

## 3. B — Sound effects

### 3.1 Approach

**Synthesize on the fly with the Web Audio API**, no audio files at all. Rationale: no need to license audio assets; doesn't add to the Service Worker's precache size; works offline by nature; pitch and duration can be tuned any time. It matches the restrained "ink and paper" visual language — a short synthesized tone fits better than a recorded sound effect.

Wrapped in a single module `src/lib/sound.ts`, exposing a semantic interface externally (e.g. `playGrade(grade)` / `playQuizResult(correct)` / `playSessionDone()`), so callers never touch Web Audio details. If it's ever switched to audio files, only that module changes.

### 3.2 Where sounds fire

Only three places:

| Event | Sound |
|---|---|
| The four grading buttons | four short tones, pitch going **upward** from Again → Hard → Good → Easy, matching the existing "hot→cold" four-color temperature band |
| Quiz correct/incorrect | two clearly distinct short tones |
| Review session complete | one slightly longer completion tone |

**No sound on card flip or bottom-nav switches** — every card gets flipped, adding a sound there would quickly become noise.

### 3.3 Constraints

- **On by default.** A toggle on the Settings page, stored in `progress.settings`, synced to other devices along with progress.

  > **This sentence was false when it was written.** `mergeProgress`'s last line at the time was `settings: local.settings` —
  > the merge always takes the local copy, so `settings` **could never sync** between two devices:
  > A changes it and pushes, B pulls it down and merges, the local copy wins, and pushing back
  > overwrites A's change. The user first ran into this with the daily new-word count.
  > Changed to resolve by `settings.updatedAt` (the same approach used for word-progress
  > resolution by `lastReviewedAt`), with a missing timestamp treated as oldest, so "a device that
  > has never changed a setting" follows "a device that has." Lesson: before writing an assertion
  > like "synced along with progress," check the merge rule — don't assume everything
  > in `progress.json` automatically syncs.
- **iOS requires `AudioContext` to be unlocked during the first user gesture**, otherwise subsequent playback fails silently. This is the most common failure mode for this kind of feature, and `resume()` must be called on the first user interaction (e.g. successful login or the first grading tap).
- Not affected by `prefers-reduced-motion` — that media query targets motion effects; sound is controlled by its own independent toggle.
- Moderate volume, duration kept to the low hundreds of milliseconds, to avoid being confused with system notification sounds.

### 3.4 Acceptance criteria

- Completely silent when the toggle is off; all three spots sound as expected when on.
- Sounds fire after the first interaction on iOS Safari (this must be verified on a real device).
- Sound effects work fine offline (synthesis doesn't depend on the network).
- Toggle state is consistent after logging in on another device.

## 4. C — Usage-frequency scoring

### 4.1 Data model

Add an **optional** field to `Word` in `src/types.ts`:

```ts
/** Contemporary likelihood of encounter, 1–10: how likely you are to run into this word in real-world context. Absent means not yet scored. */
usageScore?: number
```

**Optional, not required**: words the user adds manually in the app won't have a score, and `AddWord` shouldn't add an input for it just for this. The detail page doesn't render that row when absent, rather than showing 0.

**Compatibility**: neither `scripts/validate-words.ts` nor `src/state/sync.ts`'s `isWord` checks for extra fields, so old and new data are compatible both ways — an older app reading new data doesn't break, and a newer app reading old data just doesn't show a score.

**Validation**: `validate-words.ts` gets one more rule — if `usageScore` is present, it must be a 1–10 integer; if absent, it passes.

### 4.2 Scoring standard

The scale is anchored to **"where you'd encounter it,"** not an abstract frequency number.

| Score | Meaning | Example |
|---|---|---|
| 9–10 | Shows up in work emails and news headlines; not knowing it directly blocks comprehension | `status quo`, `due diligence` |
| 7–8 | Shows up regularly in mainstream media and business/tech reporting body text; you might well run into it in weekly casual reading | `ad hoc` |
| 5–6 | Common in formal writing, rare in speech; **or** high-frequency within a specialist field and rare outside it | `concoct`, `nonrepudiation` |
| 3–4 | Occasionally shows up in serious long-form writing, literature, legal text; barely used in contemporary daily life | `abrogate` |
| 1–2 | Rare or archaic, essentially living only in dictionaries and exam-prep material | `grandiloquence`, `circumlocution` |

**Two rules that must be treated as hard rules:**

1. **Specialist terminology is uniformly placed at 4–6**, scored by how frequent it is within documents in that field, not by general-corpus frequency. Otherwise the batch of infosec, medical, chemistry, and rhetoric terms would all get pushed down to a 1 — and they were specifically added back in when the word list was built. Only give a word 7+ once it has spilled over into everyday language (e.g. `algorithm`, `bandwidth`).
2. **Every scoring batch must carry the same set of anchor words and their assigned scores**, forcing every batch to use the same ruler. Without this step, a dozen-plus batches would each drift independently, and a 7 in one batch wouldn't be comparable to a 5 in another. This is something that wasn't done when the word list was generated in Phase 2, and in hindsight should have been.

### 4.3 Generation pipeline

- Score in batches, roughly 40 words per batch, can be dispatched in parallel.
- Each batch's prompt includes: the tier table, the two rules, and the anchor words with their scores.
- After merging, check the **distribution**: if ninety percent of words are crammed into tiers 1–3, the standard wasn't actually applied, and that batch should be re-scored rather than accepted as-is.
- Written back to `data/words.json` after passing `npm run validate-words`, then pushed to `volcab-data`.

**Overwrite strategy**: overwrite directly. It's been verified that the local `data/words.json` and the copy in `volcab-data` are byte-for-byte identical (matching SHA-256, 476-for-476, no additions/deletions/edits), so no merge logic is needed. **If the user has since modified the word list in the app, this strategy is invalid, and it must switch to "backfill fields word-by-word against the cloud copy as the baseline."**

### 4.4 Display

**Entry detail page only**, adding one more slot next to the existing four learning-status stats (state / due / review count / lapse count), reusing the already-promoted `.stat` primitive. The word-list page and review card **don't show it** — the list is already dense at 476 rows, and the review card should stay focused on memorization itself.

### 4.5 Acceptance criteria

- All 476 words have a score, every value is a 1–10 integer, `npm run validate-words` passes.
- The distribution spans multiple tiers, not ninety percent piled into one or two.
- Spot check: words like `status quo` are clearly higher than words like `grandiloquence`; specialist terms land at 4–6 and aren't pushed down to 1–2.
- The detail page shows the slot; manually added entries with no score don't show the slot and don't error.

## 5. D — Learning-data visualization

### 5.1 Data boundary (a key constraint)

The design doc's "non-goals" explicitly rules out storing a full review log — `progress.json` keeps only four aggregate numbers per day: `reviewed` / `newLearned` / `correct` / `quizTaken`. **This feature does not change that structure.**

The reasoning isn't just "follow the original design": `progress.json` and `words.json` go through the same GitHub Contents API, and are equally bound by the 1 MB read limit. At roughly 50 cards a day and about 80 bytes per log entry, a year would be about 18,000 entries ≈ 1.4 MB — meaning a new device would be unable to log in after roughly 9 months. A full log would need an archiving scheme or a different storage approach, which is out of scope here.

**So this feature can do**: daily review volume, accuracy trend, streak length and breaks, mastery growth over time, word-list status distribution, cumulative totals.
**So this feature cannot do**: per-word review history, time-of-day efficiency analysis, per-card time-on-card, forgetting-curve fitting.

### 5.2 Placement

- **A new "Recent" block below the Today page**: a bar chart of the last 7 days' review volume + accuracy, visible at a glance.
- **A new `/stats` page** carries the full statistics, entered from the "Recent" block on the Today page.
- **Doesn't take the fifth bottom-nav slot** — the four slots (Today/Library/Test/Settings) are already full, and squeezing in a fifth would hurt the mobile feel.

### 5.3 Metrics list

- Daily review volume for the last 30 days (bar chart)
- Accuracy trend
- Streak length, and a calendar of broken streaks (which day it broke)
- Word-list mastery distribution: not studied / learning / mastered
- Cumulative: total review count, number of mastered words
- Average daily new-word throughput

All derived from `dailyStats` and each word's `state`, **no charting library introduced** — hand-drawn SVG/CSS using existing design tokens, consistent with existing primitives like `.progress` and `.stat`.

### 5.4 Acceptance criteria

- With no data (a new user), every chart shows a sensible empty state, no `NaN` or blank areas.
- No error with only one day of data.
- No horizontal overflow at 375px; readable in both light and dark themes.
- Derived values match a manual calculation against `progress.json`.

## 6. E — Staging area for new words

### 6.1 Motivation

Filling out a proper entry on a phone takes ten fields, and if you don't jot the word down the moment you see it, you'll forget it. **Capture and completion have to be separated**: on the device, just record the word; completion is handled by the AI in-session, in batches.

### 6.2 Data location

A third file, **`staging.json`**, added to `volcab-data`:

```json
{ "version": 1, "items": [ { "headword": "ostensible", "addedAt": "2026-07-25" } ] }
```

**Why a separate file rather than folding it into the existing two**: putting it in `words.json` would mean half-finished entries fail schema validation, and would drop straight into the review queue; putting it in `progress.json` would pull it into the per-word merge logic designed for learning progress. A separate file = its own conflict domain.

**Entries have only two fields.** No notes, no source, no dictionary pre-lookup — the user explicitly asked for "when adding, it's just the word, everything else is produced by AI." If sense disambiguation is needed during completion, the AI decides on its own during generation, or asks the user back in-session.

### 6.3 Capture entry point

Reuses the existing `/add` route, **no new nav item added**:

- The **top** of the page is quick capture: a text input + "Add to staging." This is what's shown by default.
- The existing full form stays below (or collapsed), for the "I want to fully add this right now" scenario.
- The page shows the current staging count ("N pending"), so the user knows how many have piled up.
- Deduplication: after normalizing case and leading/trailing whitespace, a word already in `words.json` or already in `staging.json` is flagged directly rather than being added again.

### 6.4 Sync

`staging.json` needs to be wired into the sync engine, but with much simpler rules than `progress.json`:

- **Merge = union by normalized headword**, keeping the earlier `addedAt` for the same word. Mostly append-only, naturally idempotent, doesn't need the per-word `lastReviewedAt`-style comparison.
- Follows `words.json`'s push timing (push immediately on change, no debounce) and conflict-retry strategy.
- Offline capture lands locally first, merges and pushes once back online — the same pending-push-queue mechanism used for existing word-list changes.

### 6.5 Completion flow (in-session, not in-app)

1. Read `staging.json`.
2. Generate complete entries in batches, reusing Phase 2's generation prompt, and **produce C's `usageScore` at the same time** (do both in one pass — don't let new words end up missing a score).
3. Run through `npm run validate-words`.
4. Merge into `words.json` (upsert by id), **remove the promoted entries from `staging.json`** (removed exactly by headword, not by clearing the whole file — the user may have added new words while this was in progress).
5. Push both files.

Generated entries **go straight into the word list and into review**, no pending-confirmation state. If one turns out wrong, use the "delete from the review card" feature from A to remove it on the spot.

### 6.6 Acceptance criteria

- Type a word on the phone → add to staging → visible on another device after logging in.
- Duplicate words and already-listed words are correctly blocked.
- Captured offline, auto-syncs once back online.
- After completion, `staging.json` only has the promoted entries removed; words added in the meantime are still there.
- Newly listed entries carry `usageScore` and pass schema validation.

## 7. F — New quiz question types

### 7.1 Goal

The existing three question types (see word pick meaning / see meaning pick word / spelling) only cover "Chinese-English recognition" and "spelling." Add three more, expanding memorization from isolated word meaning to **real-world usage, collocation, and the semantic network**.

### 7.2 Data feasibility (measured, not estimated)

Full statistics across the 476 words:

| Candidate | Question-generation coverage | Verdict |
|---|---|---|
| Example-sentence cloze | **100%** (86% of examples contain the headword's base form, 14% contain only an inflected form, 0% can't be located) | adopted |
| Collocation fill-in | **100%** (every entry has ≥2 collocations) | adopted |
| Synonym/antonym-prompt pick-the-word | synonym 97% (≥3 synonyms), antonym 83% (≥1 antonym) | adopted |
| Antonym four-choice | **only 18%** (≥3 antonyms) | **rejected** |
| Listen-and-pick-the-word | 100% | not doing this round |

**Why "antonym four-choice" was rejected is worth recording**: four-choice needs 3 distractors, and only 18% of entries have ≥3 antonyms, so the question pool would keep pulling from the same small batch of words. **But flipping the question direction** (show an antonym, pick the target word, draw distractors from other headwords) only needs 1 antonym, and the feasible rate jumps to 83%. Same underlying knowledge point, the question direction is what determines feasibility.

### 7.3 The three new question types

**Example-sentence cloze** — take one of the word's examples, replace the headword with `___`, pick from four headwords.
- In 14% of examples the headword appears inflected (`concocted` / `concocting`), which needs to be located by stem and replaced as a whole, not matched as a whole word only.
- After blanking, the chosen example sentence **must not still contain the headword elsewhere** (to avoid a second occurrence in the same sentence leaking the answer).
- Options are the four headwords in their **base form**, inflected forms aren't restored — this incidentally also tests "does this word fit this context."

**Collocation fill-in** — take a collocation (e.g. `abrogate a treaty`), blank out the headword portion → `___ a treaty`, pick from four headwords.

**Synonym/antonym-prompt pick-the-word** — the prompt is a synonym or antonym (the UI must indicate which one), pick from four headwords.
- **Must exclude synonyms shared across multiple entries**: measured, 228 of 1597 synonyms appear in more than one entry (e.g. `overbearing`, `decree`, `flexibility`). Using one of these as a prompt would result in "two options are both correct," and the user would judge the quiz as broken.
- Distractors also need to be checked: they must not include another entry that also has that same prompt word.

### 7.4 Question-type rotation

Keep the existing **deterministic rotation** (`types[i % types.length]`), only expand the type list. Rationale: rotation guarantees a balanced distribution of question types per round, avoiding a run of bad luck from randomness like "three spelling questions in a row." 6 question types, 10 questions a round, each appearing 1–2 times — interleaved practice is itself beneficial for memory, not treated as a downside.

**No question-type selector**: it would add a settings item and UI complexity, and the benefit would be letting users avoid question types they're weak at, which runs counter to the original intent of "reinforcing memory from multiple angles."

### 7.5 Impact on existing tests (must be deliberate)

The existing assertion in `src/lib/quiz.test.ts`, `expect(new Set(qs.map(q => q.type)).size).toBe(3)`, **will necessarily fail** once question types are expanded. This is the first time this project needs to modify an existing test assertion, and it must be treated as an explicitly recorded change, not something casually fixed in passing during implementation. The revised assertion should express the actual intent: **question types rotate in a balanced way within a round**, rather than hardcoding a specific number.

All generation logic for the new question types lives in `src/lib/quiz.ts` (pure functions, already has a test file), **TDD is mandatory**.

### 7.6 Acceptance criteria

- All six question types can generate questions, and are balanced across a 10-question round.
- Example-sentence cloze: no headword remains at the blank; the 14% of entries with inflected forms are still blanked correctly.
- Collocation fill-in: the prompt doesn't contain the answer word.
- Synonym/antonym questions: the prompt indicates synonym vs. antonym; no case of two options both being correct (specifically verified against the 228 shared synonyms).
- Still degrades correctly when the word list has fewer than 4 words (existing behavior unchanged).

## 8. Cross-cutting constraints

- **No new npm dependencies.** Sound effects use Web Audio, charts are hand-drawn.
- **Stick to the existing design system**: already-promoted primitives like `.stat` / `.empty-state` / `.confirm-dialog` / `SyncStatus`; vermillion is used only as an annotation color; hairline strokes rather than shadows; `--tap: 44px` minimum tappable area.
- **Anything with real logic gets mandatory TDD and its own file**, consistent with Phase 3 (cards-remaining calculation, stats-derivation functions, etc.). No component tests for the UI itself.
- **Implementation order A → F → D → B → C → E**, each independently shippable, none blocking another. F immediately follows A (both belong to the review/quiz experience, and are pure logic changes); C comes before E, so new words E completes already carry `usageScore` on intake.

## 9. Non-goals

- No changes to `progress.json`'s structure, no review log stored.
- No forgetting-curve fitting, time-of-day analysis, or per-word history.
- No charting library or audio assets introduced.
- No changes to the SRS scheduling algorithm itself.
- No manual entry UI added for `usageScore`.
- Doesn't take the fifth bottom-nav slot.
- No "pending confirmation" state for the staging area, no in-app entry-review UI.
- Staged entries don't record notes, source, or the original sentence — capture has to stay a single-input-box cost.

## 10. Known outstanding risk (out of scope here, but related)

- `words.json` already sits at 53% of the GitHub Contents API's 1 MB read limit (559,937 bytes / 476 words); roughly another 415 words would hit the ceiling, at which point new devices would be unable to log in. The fix is to switch to `Accept: application/vnd.github.raw` on read, raising the limit to 100 MB, with the change concentrated in `getFile` in `src/lib/github.ts`. The fields C adds will make this file modestly bigger, and the ratio should be re-measured when C is implemented.
